# Playbook: from an empty repo to an app that ships itself

Distilled from Lodebreaker (Oct 2026), which shipped about fifty TestFlight builds this way. Read it once per new app; Claude sessions read `CLAUDE.md`, which `tools/init.mjs` turns into the app's own notes.

## What you get
- A single-file web app (`src/` concatenated into one page, no dependencies) with a tiny starter (a tap-to-move dot and a saved counter) that already has the bones: saves through `persistKey`, a save version with migrations, a frame loop that cannot freeze, the build id on screen.
- Smoke tests on headless Chromium (`tools/smoke/`), a build that refuses the mistakes that broke Lodebreaker.
- A Capacitor 8 iOS shell (`app/`) with native saves and haptics, Xcode Cloud scripts, a privacy manifest, and icon and splash generation. The iOS project is generated by a cloud session; the Mac is needed only to sign in and create the Xcode Cloud workflow.
- The `/ship` skill and `tools/ship-status.mjs`, so a cloud session ships and verifies everything itself, and `/ship-ios` for a Mac fallback session.

## The loop
```
you: "make the dot green" (any device)
  Claude cloud session: edit → smoke → commit → build → git push -u origin main && git push origin main:testflight
    Cloudflare Pages: builds main → https://<app>.pages.dev (about a minute)
    Xcode Cloud: builds testflight → TestFlight (5 to 15 minutes) → post-actions: internal group, and "Friends" + Beta App Review
  Claude: tools/ship-status.mjs --wait --fix in the background → "build 12 · TestFlight build 7 · both groups · the web serves it"
you: test on the phone, send the next batch
```

## One-time setup
**Who:** *You* = the owner, on a website or phone. *Claude* = a cloud session on the app's repo at claude.ai/code. *Mac* = your Mac, by hand or through a Mac Claude session with computer use. Steps marked **(once)** are done for the first app only; for every later app skip them. Write each finished step as one line in `docs/HISTORY.md`.

### 0. Where this lives
This track is the `ios-web/` folder of `nolanreed18/app-template`, beside the Streamlit + Neon blueprint at the repo root. Use this track for a phone game or app that ships to the web and TestFlight; use the root blueprint (`/new-app`) for a Streamlit + Postgres personal app.

### 1. The app's repo — You, then Claude
Create an empty private repo for the app on GitHub (github.com/new, named after the app; Claude's GitHub integration can push but cannot create repos) and give Claude access: https://claude.ai/connect-github → the Claude GitHub App → Configure → add the new repo (skip if it has all repositories). Open a cloud session at claude.ai/code on the new repo and say: "Start this app from nolanreed18/app-template's ios-web track." Claude attaches app-template, copies everything inside `ios-web/` to the new repo's root (including `.claude/` and `.gitignore`), commits and pushes. **Check:** the new repo's root has `PLAYBOOK.md`, `tools/`, `src/`, `app/` and `.claude/skills/ship/`.

### 2. Cloudflare Pages — You
dash.cloudflare.com → Workers & Pages → Create → Pages → Connect to Git → the repo. Project name = the subdomain you want (`<name>.pages.dev`; if it is taken Cloudflare adds a suffix, so use the URL it shows). Production branch `main`, framework preset None, build command `node tools/build.mjs --web`, output directory `web`, environment variable `NODE_VERSION` = `22`. Then Settings → Builds → Branch control: no preview deployments (pushes to `testflight` should build nothing here). **Check:** the URL shows the starter with `web · <date> · <sha>` at the bottom.

### 3. Init — Claude
Start a cloud session on the repo and say: *Run init with name "My App", bundle id com.yourname.myapp, web https://myapp.pages.dev, then build, smoke, commit and push.* It runs
```sh
node tools/init.mjs --name "My App" --id com.yourname.myapp --web https://myapp.pages.dev \
  [--team <Apple team id>] [--issuer <App Store Connect issuer id>] [--mac-key <Mac key id>] [--email <privacy contact>]
node tools/build.mjs && node tools/smoke/run.mjs
git add -A && git commit -m "Start My App from the app template"   # trailer: Co-Authored-By: Claude <noreply@anthropic.com>
node tools/build.mjs && git add index.html && git commit --amend --no-edit && git push -u origin main
```
The team, issuer, Mac key id and email are the same for every app on the account: copy them from the previous app (Lodebreaker: `tools/ship.config.json` and `app/ios/ExportOptions.plist`). Bundle ids take letters, digits, hyphens and dots, and can never change once the App Store record exists. **Check:** init's "Left to fill" lists only the App Store Connect ids; the web shows the app's name.

### 4. Apple: the program, the app record and the groups — You
1. **(once)** Join the Apple Developer Program (99 USD a year) and accept the agreements in App Store Connect.
2. Register the bundle id: developer.apple.com → Certificates, Identifiers & Profiles → Identifiers → + → App IDs → App → Explicit → the id from step 3.
3. App Store Connect → Apps → + → New App: iOS, a name, language, that bundle id, SKU = anything (the slug). The name must be unique on the whole App Store; if it is taken add a subtitle ("Lodebreaker: Ice Moon"); the home-screen name stays the app's own.
4. App Information → Privacy Policy URL: `https://<app>.pages.dev/privacy.html` (the web build serves `docs/privacy.html`; keep it true).
5. TestFlight → Internal Testing → + → **"<App name> Internal"** (the name init wrote in `tools/ship.config.json`); add yourself.
6. TestFlight → External Testing → + → **"Friends"** → turn on the public link (testers can join once a build passes review).
7. TestFlight → Test Information: beta description, feedback email, Beta App Review contact (name, phone, email), sign-in not required. Apple will not review an external build without it.

**Check:** the app shows in App Store Connect with both groups.

### 5. The iOS project, icon and splash — Claude
```sh
cd app && npm ci && npm run add-ios && npm run assets
```
`add-ios` builds `www/`, runs `npx cap add ios` and `tools/ios-setup.mjs`, which lays `app/ios-template` over `app/ios` (Xcode Cloud's `ci_scripts/ci_post_clone.sh`, `PrivacyInfo.xcprivacy`, the shared `App` scheme Xcode Cloud builds, `ExportOptions.plist`) and patches the project (privacy manifest as a resource, bundle id, team, home-screen name, `ITSAppUsesNonExemptEncryption` = false so no build waits on the export compliance question). `assets` draws `app/assets/icon.png` and `splash.png` (title inside the central 38%: the splash is shown aspect-fill) and generates the asset catalog; replace the art in `tools/assets.mjs` with the app's own when it has some. All of it runs on Linux. Commit `app/` and push main. **Check:** `CI_PRIMARY_REPOSITORY_PATH=$PWD sh app/ios/App/ci_scripts/ci_post_clone.sh` from the repo root prints the build id with no `+` and the What to Test text, and `git status` stays clean.

### 6. App Store Connect API keys (once) — You
App Store Connect → Users and Access → Integrations → App Store Connect API (the first time, the Account Holder clicks Request Access). Team Keys → + :
- **"Claude cloud", App Manager** access, for the cloud environment (reads Xcode Cloud and builds, adds builds to groups, submits for review). Download the `.p8` (Apple offers it once) and note the Key ID and the **Issuer ID** at the top of the page.
- **"Mac uploads", Admin** access, only if the Mac will ever upload builds itself: exporting for the App Store re-signs with Apple's cloud-managed certificate, which refuses lesser roles. Move it to `~/.appstoreconnect/private_keys/AuthKey_<KEYID>.p8`, `chmod 600`, and put the id in `tools/ship.config.json` (`node tools/init.mjs --mac-key <KEYID>`).

Never paste a key into a chat, commit it, or send it anywhere. A lost or leaked key: revoke it on the same page and make another. **Check:** the page lists the keys.

### 7. The Claude cloud environment (once, plus each app's host) — You
At claude.ai/code, the environment menu in a session's title bar → Edit. One environment serves every app.
- **Network access:** Limited. **Allowed domains:** `api.appstoreconnect.apple.com` and the app's host (`<app>.pages.dev`; add each new app's host). Leave "Allow package managers" ticked (npm needs it).
- **Environment variables** (not Network secrets: the scripts sign a token with the key themselves): `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_KEY_P8` = the `.p8` as one line (on the Mac: `base64 -i AuthKey_<KEYID>.p8 | tr -d '\n' | pbcopy`, then paste; the raw file text works too).
- **Permission mode:** pick **Auto** in the dropdown next to the prompt box. Cloud sessions ignore `bypassPermissions` in settings files; `.claude/settings.json` already allows every tool a ship uses, and is read when the session has this one repository.

**Check**, in a new session (settings reach new sessions only): `node tools/asc.mjs GET /apps` prints 200 and lists the app; `curl -sI https://<app>.pages.dev | head -1` prints 200.

### 8. Xcode and the Xcode Cloud workflow — Mac
By hand, or say "set up Xcode" to the Mac Claude session (step 10), which does it with computer use.
1. **(once)** Install Xcode, open it once, Settings → Accounts → add your Apple Account. Install Node 22 or newer.
2. Clone the repo; `cd app && npm ci && npm run ios` (syncs and opens Xcode). App target → Signing & Capabilities: automatic signing, your team.
3. Integrate → Xcode Cloud → Create Workflow → the App product. Grant Xcode Cloud access to the GitHub repo when asked (the Xcode Cloud GitHub app; if it is limited to selected repos, add this one on GitHub). Accept the default workflow: Xcode's sheet takes clicks but not typed text from computer use, so shape it on the website.
4. App Store Connect → the app → Xcode Cloud → Manage Workflows → the workflow → Edit (Xcode's Integrate → Manage Workflows edits the same thing):
   - Name **TestFlight**; Environment: Xcode and macOS "Latest Release".
   - Start Conditions: remove the default; add **Branch Changes → Custom Branches → `testflight`** only (pushes to main then spend no build hours).
   - Actions: **Archive**, iOS, scheme App, Deployment Preparation **TestFlight and App Store** (an "Internal Testing Only" archive can never join an external group).
   - Post-Actions: **TestFlight Internal Testing** → the internal group; **TestFlight External Testing** → Friends (it submits for Beta App Review too). The App Store Connect API can neither read nor add post-actions, so this website (or Xcode) is the only place they are made, and no script can check them.
   - Save. Saving here can clear the branch start condition, so check it again afterwards: `node tools/asc-ids.mjs` reads it, and `node tools/asc-ids.mjs --fix-branch` sets it back through the API (or re-add it on the page).
5. Xcode Cloud → Settings → Build Number: **Next Build Number** above any build already uploaded from the Mac (nothing uploaded yet: leave it).

**Check:** step 9's `asc-ids` prints ok for the product, the workflow, the branch condition and the audience; the post-actions you see on the website, and the first ship (step 11) proves them: the build lands in both groups with no `--fix` line.

### 9. Fill the ids — Claude
`node tools/asc-ids.mjs --write` finds the app by bundle id, both groups, the public link and the workflow, checks the start condition (add `--fix-branch` to set it) and the archive audience, and writes `tools/ship.config.json`. Post-actions are not in the API: it cannot see them. Commit it as `Notes: App Store Connect ids`, push main, and put the App Store Connect name and public link in CLAUDE.md's Live build. **Check:** no MISS lines; `node tools/ship-status.mjs` reports "no run for this commit yet" instead of SETUP.

### 10. Optional: the Mac fallback session (once per Mac) — You
Only needed when the cloud cannot reach App Store Connect or Xcode Cloud cannot build.
- `~/.claude/settings.json`: `{"permissions":{"defaultMode":"bypassPermissions"}}`, so the session never stops to ask. The trade-off: it runs whatever the repo's tools contain, and any session that can push can change them.
- The Admin key from step 6 in `~/.appstoreconnect/private_keys/`; `npm i -g playwright-core` for the smoke suite on the Mac.
- Claude desktop app → Settings → Claude Code → Remote Control → add the repo folder (a git root, not inside a hidden folder or ~/Library), or run `claude remote-control` in it. Turn on computer use (Settings → Computer use; grant Accessibility and Screen Recording).
- Start a session there, title it "<App> · ship (Mac)", and give its session id to the cloud session for CLAUDE.md's Live build.

**Check:** from the cloud, `list_sessions` shows it as a connected "bridge" session, and a one-shot `create_trigger` (`persistent_session_id` = it, `run_once_at` = now + 2 minutes) saying "ship check" starts a turn there (`list_events`).

### 11. The first ship — Claude, then You
Say "ship". The session pushes main and testflight and waits on ship-status. The first external build of a version needs a full Beta App Review (usually within a day), so the first wait ends at 45 minutes with `external WAITING_FOR_BETA_REVIEW`: expected. Apple reviews one build per version at a time; once the first is approved, later builds of the same version pass at once. **Check:** the end-to-end list below.

**The second app onward:** steps 1, 2, 3, 4.2 to 4.7, 5, the host in 7, 8.2 to 8.5, 9, 11. Everything else is already done.

## Every change
1. Tell a cloud session on the repo what to change; batch several items in one message. Paste testers' reports as they come.
2. It edits, adds a smoke check for anything new, and ships (`/ship`, or it ships on its own after a batch). One push per batch: a second testflight push within about ten minutes cancels the running build.
3. It reports the build id, then the TestFlight build, both groups and the web when ship-status exits. The web updates in a minute or two, TestFlight in 5 to 15.
4. A new chat starts from `CLAUDE.md` (the current truth) and `docs/HISTORY.md` (the dated log); nothing else carries over.

## Lessons from Lodebreaker
**Shipping**
- Commit, then build, then amend the built page: the build id (`build <count> · date · sha`, `+` when dirty, `web` on Cloudflare's shallow clone) is how you know which commit a phone or the web runs. Check it after every ship.
- `git push -u origin main && git push origin main:testflight`: `&&`, never `;` (build 145 sent testflight a commit that was not on main after main was refused). Never push testflight anything not on main.
- Batch: a second testflight push within about ten minutes cancels the running Xcode Cloud build (two builds never uploaded that way).
- Commit subjects become TestFlight's What to Test: write them for testers. Notes-only commits start with `Notes:` and go to main only.
- Keep model names out of commits, trailers included: `Co-Authored-By: Claude <noreply@anthropic.com>`.
- A public shared Claude artifact asks the owner for permission on every publish, whatever the settings: ships never republish one; the web build is the link to share.

**Apple and Xcode Cloud**
- The archive audience must be "TestFlight and App Store"; an internal-only build can never join the external group.
- Xcode Cloud numbers builds itself: its Next Build Number must stay above any Mac upload ("The bundle version must be higher than the previously uploaded version").
- Post-actions exist only on the website (or Xcode's Manage Workflows): the API cannot read or add them. Saving the workflow there can clear its Branch Changes condition, and a push can start no run: `asc-ids` checks the condition and `--fix-branch` restores it through the API; `POST /ciBuildRuns` starts a run by hand.
- The internal group's automatic distribution did not pick up cloud builds: use the Internal Testing post-action. An external build needs a Beta App Review submission, which the External Testing post-action (or `ship-status --fix`) makes; without it the build sits at READY_FOR_BETA_SUBMISSION.
- Apple answers 403 on some endpoints to every key: a build's groups come from `GET /betaGroups?filter[builds]=<id>`, not `/builds/<id>/betaGroups`. A 403 is a closed route as often as a short role: try another route to the same data before blaming the key.
- `ITSAppUsesNonExemptEncryption` = false (ios-setup sets it), or every build waits on the export compliance question. `PrivacyInfo.xcprivacy` declares UserDefaults (reason CA92.1) for Preferences, or App Store Connect flags the upload.
- `npm run sync` before any xcodebuild, or the archive ships the previous web assets (it happened; `ship-ios.sh` checks the archive's build id). `ci_post_clone.sh` unshallows the clone so the commit count is right.
- Upload with an API key, not Xcode's Apple ID session (it once lost App Store Connect access mid-ship); the upload key must be Admin.
- The App Store display name may be taken; the home-screen name is separate. Turn on Developer Mode and trust the developer before a first device run; the Simulator's WebView takes 15 to 20 seconds to paint.

**Code**
- No bundler: Capacitor plugins only through `Capacitor.nativePromise(plugin, method, opts)`; `registerPlugin` lives in `@capacitor/core`'s bundle, which the page never loads, so calls through it failed silently.
- Pad the top bar with `env(safe-area-inset-top)` and never let a later `padding` or `padding-block` override it (the HUD sat under the Dynamic Island).
- `src/` files share one scope: a repeated top-level function silently replaced another and froze every Ground Slam for a day; the build now refuses duplicates.
- Never append a `//` comment to a line with code after the insertion point: it swallowed `heavyTick();` and broke the game twice in one day.
- A throw inside `draw()` stopped `requestAnimationFrame` for good (a tester's frozen game, Oct 30): ask for the next frame first and keep the smoke check that frames keep coming. Bound id ranges on both ends; a bare `v>=X` took new tile ids for old ones.
- iOS can evict WebView storage: mirror saves to Preferences (`persistKey` and `native.js` do), save on hide, version every save and migrate old ones.
- Phones: tap targets of 30 px or more counted on `pointerdown` (quick taps on small text were eaten as double-tap gestures); per-frame DOM writes cause judder, so throttle them (about 12 Hz) and move bars with `transform`. Web Audio must be resumed inside a touch on iOS.

**Tests and tuning**
- Smoke waits poll the app (`p.until`), never sleep: fixed sleeps went flaky on a loaded machine.
- Run the smoke suite before every ship and add a check with every feature; reviewers' repro scripts become checks.
- Measure before tuning: bots that drive the real `step()` caught balance and pacing problems that play-feel missed.

**Claude sessions**
- Cloud: Auto mode; `.claude/settings.json` holds the allow list. The cloud cannot see the Mac's key; it reads App Store Connect through the App Manager key in its environment.
- A `send_message` to an idle Remote Control session only queues; a one-shot `create_trigger` wakes it (re-read the clock first: a worker restart makes a precomputed `run_once_at` stale). Its replies never reached the cloud chat and `send_later` into a cloud session failed ACCESS_DENIED: wait with a background `sleep` and read its transcript with `list_events`.
- Background commands stop at 30 minutes unless given a longer `timeout`; `ship-status --wait` needs 50.
- Node's fetch ignores `HTTPS_PROXY` without `NODE_USE_ENV_PROXY=1`; `asc-lib.mjs` re-runs itself with it.
- `ship` is edited only from cloud sessions and `ship-ios` only from the Mac; pull before editing either (both once edited the same file at once).
- Keep `CLAUDE.md` under 40 KB with dated history in `docs/HISTORY.md`: Lodebreaker's notes reached 120 KB and every session paid for it.
- **IP rule** for genre-inspired apps: everything original (name, art, sound, text, store keywords), no close imitation; check the name for trademarks before the listing.

**When ship-status says**
| | |
|---|---|
| `SETUP: no App Store Connect key` / `no issuer id` | step 7's environment variables, then a new session |
| `unreachable` / `network: ...` | the host is missing from step 7's Allowed domains |
| `the key was refused (401)` | key id, issuer and `.p8` do not belong together |
| `-> 403` on a GET | the key is short of App Manager, or Apple closes that endpoint to keys: read the same data another way (as with a build's groups) |
| `placeholders: appId, workflowId, ...` | step 9 |
| `Xcode Cloud: no run for this commit yet` (after 2 minutes) | the push started no run: `node tools/asc-ids.mjs --fix-branch`, then start one with `POST /ciBuildRuns` |
| run `FAILED` | `node tools/asc.mjs GET /ciBuildRuns/<id>/actions`, then `/ciBuildActions/<id>/issues` |
| `-Friends` or `READY_FOR_BETA_SUBMISSION` | the External Testing post-action is missing; `--fix` does it meanwhile |
| `WAITING_FOR_BETA_REVIEW` | the first external build of a version: Apple reviews it, usually within a day |

## Verify the whole pipeline on a fresh app
After setup, once, and again whenever the pipeline changes. Record each result in `docs/HISTORY.md`.
1. Claude: `node tools/build.mjs && node tools/smoke/run.mjs` passes; `node tools/asc-ids.mjs` prints no MISS.
2. You: ask for a visible change ("make the dot green") and "ship".
3. Within a few minutes the web shows it, and ship-status's web line says it serves the pushed commit (`web · date · <sha>`).
4. ship-status exits 0: `Xcode Cloud run N: COMPLETE SUCCEEDED`, `TestFlight build N VALID · +<App> Internal +Friends · external IN_BETA_TESTING` (the first time, after the review).
5. On the phone: TestFlight offers the build with What to Test = the commit subject; the app shows the green dot and the build id of that commit; tap a few times, force-quit, reopen: the count survived (native Preferences).
6. A friend opens the public link and installs.
7. With a Mac session: ask the cloud to wake it for a ship check; its transcript ends with the three-line report.
