# Ship __APP_NAME__ (cloud session)

Order matters: commit before building so the build id is clean, and never push anything the smoke suite has not passed. The owner touches nothing.

1. **Check the tree.** `git status`; `git pull --rebase origin main` (the Mac or another session may have pushed notes). A cloud clone is shallow: `git fetch --unshallow origin main` (once; skip if `git rev-parse --is-shallow-repository` says false), or the build id counts only the fetched commits.
2. **Smoke.** `node tools/build.mjs && node tools/smoke/run.mjs`. Every test must pass. A failure is a bug to fix before shipping, never a test to skip. A feature in this batch gets a smoke check before it ships.
3. **Commit** with a plain-language subject written for testers (it becomes TestFlight's What to Test) and no model names anywhere, trailers included: end with `Co-Authored-By: Claude <noreply@anthropic.com>`. Then `node tools/build.mjs && node tools/build.mjs --web && node tools/build.mjs --app`, `git add index.html`, `git commit --amend --no-edit`. Check `index.html`'s build id has no `+` and its count equals `git rev-list --count HEAD`.
4. **Push**: `git push -u origin main && git push origin main:testflight`. Always `&&`, never `;` (Lodebreaker build 145: main was refused, the testflight push ran anyway and shipped a commit that was not on main). If main is rejected: `git pull --rebase origin main`, redo step 3's builds and amend, push again. Batch first and push once: a second testflight push within about ten minutes cancels the running Xcode Cloud build. Cloudflare Pages deploys main in a minute or two; Xcode Cloud builds testflight in 5 to 15 minutes, `ci_post_clone.sh` writes What to Test from the commit log, and the two post-actions put the build in both groups and submit it for Beta App Review.
5. **Verify, in the background.** `node tools/ship-status.mjs $(git rev-parse HEAD) --wait --fix` with Bash `run_in_background` and `timeout` 3000000 (it can wait 45 minutes; the default background limit is 30). It exits when the build is VALID, in both groups and testable (0), failed (1), still pending after 45 minutes (2), or at once when the pipeline is not set up (3, with SETUP lines saying what is missing). `--fix` adds a missing group and submits for review. Its last lines also say whether __WEB_URL__ serves the commit. Keep working or end the turn; the exit wakes this session.
6. **Report** in a few lines: the commit and build id, then, when the check exits, the TestFlight build number, both groups and the web. A failure is work, not a report: read the run's issues (`node tools/asc.mjs GET /ciBuildRuns/<id>/actions`, then `/ciBuildActions/<id>/issues`), fix, ship again. An `add to ...` or `submit for beta review` line in its output means a post-action is missing or failed: say so (the owner adds post-actions on the App Store Connect website; the API cannot). Exit 3: name the one missing setting for the owner (PLAYBOOK.md, cloud environment step), then use step 7.
7. **Fallback: the Mac** (only when step 5 cannot run and CLAUDE.md lists a Mac session). Find it with `list_sessions` (the newest "bridge" session with the title in CLAUDE.md; `get_session` shows `connection_status`). Wake it with a one-shot `create_trigger`: `persistent_session_id` = the Mac session, `run_once_at` = now + 3 minutes from a fresh `date -u` (a worker restart makes a precomputed time stale), `initiation` "own_followup", name `Ship check: build <m>`, prompt `ship check: build <m> (<sha>) pushed to testflight. Run /ship-ios check mode and end with a three-line report: the TestFlight build number, both groups, anything that failed.` A `send_message` only queues on an idle Remote Control session, its replies never reach this chat, and `send_later` into a cloud session fails ACCESS_DENIED: so wait with a background `sleep 1260` (Bash `run_in_background`), then read its last assistant text with `list_events` (kinds ["assistant"]); if its turn is still running, wait 10 minutes more the same way. No Mac connected: say so; the build still reaches both groups through the post-actions.
8. **Notes.** Update "Live build" in `CLAUDE.md` (commit, build id, TestFlight build) and add a dated line to `docs/HISTORY.md`; commit as `Notes: ...` and push main only (notes never go to testflight; `tools/whattotest.mjs` skips them).

Never: commit keys or certificates; push to testflight anything not on main; republish a public shared Claude artifact as part of a ship (every publish shows the owner a permission card no setting removes; the web build is the link to share).

This skill is edited only from cloud sessions; `.claude/skills/ship-ios/SKILL.md` only from the Mac. `git pull origin main` before editing either.
